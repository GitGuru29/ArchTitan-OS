# v3.8 — stall-aware bandwidth loaning

Date: 2026-11-25
Branch: `main` (after merging `feat/thm-cpu-pressure-engine`)

## What changed

The v3.4–v3.7 CPU engine always reserved foreground capacity at HIGH/CRITICAL
pressure, even when the protected work was idle. That protected latency, but it
left bulk throughput on the table.

v3.8 adds a `BandwidthLoanTracker` before the existing 3-tick
`AdaptiveHeadroomTracker`:

- A loan is considered only at HIGH/CRITICAL pressure, with the user present,
  at least 3 logical CPUs, and a base reservation of more than one core.
- The loan requires **5 consecutive quiet ticks**: no recent input event,
  `cpu_stall_pct >= 0` and below 5%, and foreground load below ~25% of each
  reserved core.
- It lends **one logical core**, or **one whole physical core (2 logical
  siblings)** when SMT is detected, so v3.5 whole-core isolation is preserved.
- It reclaims **in the same tick** on input, PSI stall, foreground growth,
  pressure/presence change, or a new latency/GPU workload. The old reservation
  hysteresis is bypassed when protection must grow.
- Still scheduling-only: only `cpu.max`/`cpu.weight` inputs change. HC-CPU-1
  holds — no CPU-pressure kill, stop, freeze, I/O, or GPU action.

Telemetry now exposes `bandwidth_loan_cores`, and both `titan-hwm status`
formatters print a `Bandwidth loan:` line while active.

## Unit verification — TC-46

`./build/thm_test_runner`: **46/46 PASSED**

| Case | Result |
|---|---|
| 8 CPUs, base reserve 2, 5 quiet ticks | reserve `2 → 1`, loan `1` core |
| Recent input event | reserve back to `2`, loan `0` immediately |
| PSI stall 12% | reserve stays `2` |
| Foreground 60% | reserve stays `2` |
| Pressure/presence/base-reservation change | loan cleared immediately |
| SMT 8 CPUs, base reserve 4 | reserve `4 → 2`, loan `2` logical cores |
| 2-vCPU guest, base reserve 1 | no loan |
| PSI unavailable (`-1`) | no loan |
| Policy quota with reserve override 1 | BG quota `6 → 7` 25 ms periods, no `cpu.idle` change |

## Interpretation

The loan widens the background CFS quota only while the foreground is provably
quiet, so the latency gains are unchanged and bulk work recovers part of the
reserved bandwidth. Throughput retention is still above the scorecard threshold
but is not a clean speedup measurement: the host is shared and the scorecard is
short. No QEMU compile A/B was run after this change, so no median-compile
improvement is claimed for v3.8.
