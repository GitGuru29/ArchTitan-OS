# v3.9 — Hyprland window context binding

Date: 2026-11-25
Branch: `main`

## What changed

Hyprland's `activewindow` event already delivered `CLASS,TITLE`, but THM only
used a fragile `comm.find(class.substr(0,8))` heuristic and discarded the
evidence after classification. v3.9 makes the binding explicit and auditable:

- `window_context_matches(class, comm, exe, cmdline)` is a pure matcher. It
  normalizes dots/hyphens/case, drops generic tokens (`org`, `google`,
  `jetbrains`, `visual`, `studio`, …), canonicalizes aliases
  (`chromium → chrome`, `firefoxesr → firefox`, `vscodium → code`), and compares
  the class against the process `comm`, exe basename, and argv0 basename.
- `bind_window_context()` stores the matched class/title on the workload **root**.
  Children inherit the context through the existing ownership graph.
- **Title is never binding evidence by itself.** A headless `g++ main.cpp` must
  not inherit a focused editor whose title contains `main.cpp`. Class is the
  sole authority; the title is stored only after the class matches.
- An empty/mismatched Hyprland state leaves an existing binding intact, so an
  IPC gap cannot strip valid context.
- Telemetry now emits `window_class` / `window_title` per workload and
  `titan-hwm status <workload>` prints them.

Hyprland IPC remains the **only** live context provider. No new socket, no
`hyprctl` fork, no `/proc`-only context source, no I/O/GPU plane.

## Interpretation

This change improves context fidelity and observability, not raw scheduling.
No median-compile improvement is claimed; the headless benchmark has no
Hyprland IPC and therefore exercises only the unchanged CPU path. The win is
that workload ownership now carries the exact Hyprland window evidence that
created the foreground classification, making later dependency-graph work a
query on real bindings rather than a re-guess from process names.

## Guardrails verified

- Hyprland IPC is the only live context source.
- Title alone cannot create foreground context.
- CPU pressure still produces no kill/stop/freeze signals.
- `archtitan-latency.slice` still receives no `cpu.max` or `cpu.idle`.
- Destructive memory reclaim remains opt-in.
- No I/O plane, no GPU plane, no GPU stress.
