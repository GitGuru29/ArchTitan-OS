# v3.4 QEMU/KVM A/B — regression fixed, throughput restored

Original failing commit: `cbefd6ba12079f92c81ff3ee880a37447f38b0e5`
Fix baseline: v3.4-R2 (`3980adc`)
Final fix: v3.4-R3 (this change)

## Original result (FAIL)

THM v3.4 completed **1** compile round in **468259 ms** versus **5** rounds at
**47567 ms** median with THM disabled — a **9.8x** slowdown. Swap-out was
401085 pages vs 0. The last action in arm A was `THROTTLE (g++)`.

## Root causes found

The regression was not caused by the v3.4 Hyprland recent-focus change. Four
effects stacked:

1. **Slice-wide `memory.high`** on `archtitan-background.slice`, which also held
   executing builds in the headless harness.
2. **Headless presence assumption.** With no Hyprland IPC, THM assumed a user
   was present and kept a 50% `cpu.max` cap on background work.
3. **Compiler children frozen.** Short-lived `cc1plus` children looked
   IDLE/AGING and received `FREEZE` under HIGH memory pressure, stalling the
   build without reclaiming the hog's pages.
4. **Fixed per-tick overhead.** In a 2-vCPU guest, the daemon's ~25% of one vCPU
   scan/telemetry loop and low child/parent cgroup weights materially reduced
   the CPU available to the compiler.

## Fixes

### v3.4-R2

- Added `archtitan-throttled.slice`. `THROTTLE`/`AGING` work and `memory.high`
  now land there; executing background work has no memory ceiling.
- Distinguished “Hyprland IPC never existed” (headless) from “IPC dropped.”
  Headless bulk-only hosts lift the CPU cap; a compositor disconnect still
  fails safe to PRESENT.
- Classified compiler/build executables as `throughput_bulk`. Bulk work is
  never frozen or reclaimed; executing bulk work gets `memory.low` protection.
- Added TC-44 and TC-45.

### v3.4-R3 — throughput restoration

- In headless bulk-only mode, raise the background child weight to the active
  weight (`B:1000`) and the parent `archtitan.slice` weight to `2000`, so the
  build hierarchy wins CFS share against the daemon/probe. Both weights are
  restored to normal as soon as a compositor/user signal returns.
- Extend the expensive full `/proc` metadata refresh from 1 s to 5 s only in
  headless bulk-only mode. Pressure/stat polling, new-PID classification, and
  the 200 ms tick are unchanged, so containment stays fast. Daemon CPU in the
  final arm A fell to **9.64%** of one vCPU.
- TC-38 now also asserts the headless bulk weight boost.

A more aggressive 1 Hz whole-tick experiment was tested and **rejected**: it
cut daemon CPU to ~6% but slowed pressure response enough to lose hog
containment (one 337 s round). The full-refresh-only change keeps the fast
pressure tick and does not have that failure mode.

## Final verification — exact QEMU A/B rerun

Same VM/workload as the original regression: 2 vCPU, 4 GB RAM, 2 GB swap,
live ISO `out/archtitan-2026.11.18-x86_64.iso`,
`systemd.unit=multi-user.target`. Current daemon staged from the bench disk.

Runs: `A-20261123-111029` vs `B-20261123-111822`.

| Metric | THM v3.4-R3 | THM off | Original failing THM |
|---|---:|---:|---:|
| Complete compile rounds | 6 | 8 | 1 |
| Median complete round | **38613 ms** | 33119 ms | 468259 ms |
| Median ratio vs THM off | **1.17x** | 1.00x | 9.84x |
| THM daemon CPU | **9.64% of one vCPU** | — | 33.68% |
| Swap-out pages | 0 | 0 | 401085 |
| Major faults | 3.2M | 3.3M | 22687 |
| Kernel OOM kills | 0 | 0 | 0 |
| Min MemAvailable | 375 MB | 47 MB | — |

| Slice weights | `P:2000 / A:1000 / L:950 / B:1000` | — | `B:10` |
| Last action | `THROTTLE (tstress)` | — | `THROTTLE (g++)` |

No compiler process was frozen in the final run. The only frozen workloads were
the two idle apps and the memory hog. The CPU cap reported `100.0%
(auto-lifted: user idle >60s)` throughout arm A.

The original 9.8x regression is now **1.17x** on median round time, and the
absolute median is **below 50 s** as requested.
