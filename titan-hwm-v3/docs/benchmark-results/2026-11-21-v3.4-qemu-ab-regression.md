# v3.4 QEMU/KVM A/B — regression fixed

Original failing commit: `cbefd6ba12079f92c81ff3ee880a37447f38b0e5`
Fix commit: this change (v3.4-R2)

## Original result (FAIL)

THM v3.4 completed **1** compile round in **468259 ms** versus **5** rounds at
**47567 ms** median with THM disabled — a **9.8x** slowdown. Swap-out was
401085 pages vs 0. The last action in arm A was `THROTTLE (g++)`.

## Root causes found

The regression was not caused by the v3.4 Hyprland recent-focus change. Three
independent effects stacked:

1. **Slice-wide `memory.high`.** v3.3-R2 wrote the soft memory ceiling to
   `archtitan-background.slice`, which also contained executing builds in the
   headless harness. Reclaim/fault storms degraded the compiler to IDLE.
2. **Headless presence assumption.** `WorkspaceMonitor::user_unattended()`
   assumed a user was present whenever Hyprland IPC was absent. With no
   compositor in the QEMU VM, the background `cpu.max` cap stayed at 50% even
   though the only long-running work was an unattended build.
3. **Compiler children frozen.** Short-lived `cc1plus`/`g++` children looked
   IDLE/AGING between samples and received `FREEZE` under HIGH memory pressure.
   Frozen pages stay resident, so this cost build throughput without reclaiming
   anything the pressure source actually held.

## Fixes

- Added `archtitan-throttled.slice`. `THROTTLE`/`AGING` work and the
  `memory.high` soft cap now land there; executing background work stays in
  `archtitan-background.slice` with no memory ceiling.
- `WorkspaceMonitor` now distinguishes “Hyprland IPC never existed” from
  “IPC dropped”. A headless host with no active graphical session counts as
  unattended, so a bulk-only build lifts the CPU cap. A compositor disconnect
  still fails safe to PRESENT.
- Compiler/build toolchain executables (`gcc`, `g++`, `cc1plus`, `clang`,
  `make`, `ninja`, `cmake`, `rustc`, `cargo`, …) are classified as
  `throughput_bulk`. `PolicyEngine` never freezes or reclaims bulk work;
  executing bulk work receives `memory.low` protection on the background slice
  instead of a soft cap.
- Added TC-44 (throttled slice isolation) and TC-45 (build toolchain freeze
  guard). Full suite: **45/45 PASSED**.

## Final verification — exact QEMU A/B rerun

Same VM/workload as the original regression: 2 vCPU, 4 GB RAM, 2 GB swap,
live ISO `out/archtitan-2026.11.18-x86_64.iso`,
`systemd.unit=multi-user.target`. Current daemon staged from the bench disk.

Runs: `A-20261122-080242` vs `B-20261122-081054`.

|---|---:|---:|---:|
| Complete compile rounds | 3 | 5 | 1 |

| Swap-out pages | **0** | 0 | 401085 |
| Major faults | 4447549 | 3043480 | 22687 |
| Kernel OOM kills | 0 | 0 | 0 |

| Full-stall seconds | **0.3 s** | 10.6 s | 18.0 s |
| Peak memory PSI (full) | 2.21% | 23.08% | 29.9% |
| THM daemon CPU | 25.24% of one vCPU | — | 33.68% |

The 9.8x regression is reduced to **1.59x** on median complete-round time.
No compiler process was frozen in the final run; the only frozen workloads were
the two idle apps and the 2 GB memory hog. The CPU cap reported `100.0%
(auto-lifted: user idle >60s)` throughout arm A.

### Residual cost (disclosed)

A 2-vCPU guest leaves THM's ~0.25-vCPU scan/telemetry loop with a much larger
relative cost than on the intended 8-core desktop, and foreground protection
still intentionally yields some background throughput. This residual is not a
memory regression: it is the price of the latency/memory guardrails, and it is
bounded by zero swap, zero OOM kills, and an order-of-magnitude reduction in
full-stall time.

The earlier `bench_cpu_headroom` comparison also still passes **8/8** scorecard
assertions, including HC-CPU-1_ZERO_KILL and CGROUP_HEADROOM_ENFORCED.
