# v3.4 QEMU/KVM A/B — regression fixed, throughput and daemon cost reduced

Original failing commit: `cbefd6ba12079f92c81ff3ee880a37447f38b0e5`
Fix baseline: v3.4-R2 (`3980adc`)
Throughput fix: v3.4-R3 (`e64e261`)
Final daemon-cost fix: v3.4-R4 (this change)

## Original result (FAIL)

THM v3.4 completed **1** compile round in **468259 ms** versus **5** rounds at
**47567 ms** median with THM disabled — a **9.8x** slowdown. Swap-out was
401085 pages vs 0. The last action in arm A was `THROTTLE (g++)`.

## Root causes found

The regression was not caused by the v3.4 Hyprland recent-focus change. Four
effects stacked:

1. **Slice-wide `memory.high`** on `archtitan-background.slice`, which also held
   executing builds.
2. **Headless presence assumption.** With no Hyprland IPC, THM assumed a user
   was present and kept a 50% `cpu.max` cap on background work.
3. **Compiler children frozen.** Short-lived `cc1plus` children looked
   IDLE/AGING and received `FREEZE` under HIGH memory pressure, stalling the
   build without reclaiming the hog's pages.
4. **Fixed per-tick overhead.** In a 2-vCPU guest, the daemon's scan/telemetry
   loop and low child/parent cgroup weights materially reduced CPU available to
   the compiler.

## Fixes

### v3.4-R2

- Added `archtitan-throttled.slice`. `THROTTLE`/`AGING` work and `memory.high`
  now land there; executing background work has no memory ceiling.
- Distinguished “Hyprland IPC never existed” (headless) from “IPC dropped.”
  Headless bulk-only hosts lift the CPU cap; a compositor disconnect still
  fails safe to PRESENT.
- Classified compiler/build executables as `throughput_bulk`. Bulk work is
  never frozen or reclaimed; executing bulk work gets `memory.low` protection.
- Added TC-44 and TC-45.

### v3.4-R3 — throughput restoration

- Headless bulk-only mode raises the background child weight to the active
  weight (`B:1000`) and the parent `archtitan.slice` weight to `2000`.
- Full `/proc` metadata refresh moved from 1 s to 5 s in headless bulk mode.
- TC-38 now also asserts the headless bulk weight boost.
- Result: 9.8x regression → 1.17x, absolute median 38.6 s.

### v3.4-R4 — daemon CPU reduction

Four avoidable per-tick costs were removed:

1. **No `hyprctl` popen on headless hosts.** `refresh_visibility()` shells out
   to `hyprctl monitors -j`; it is now called only when Hyprland IPC has actually
   connected. Previously this forked a doomed shell 5x/s in the QEMU guest.
2. **Governor scan on change, not every tick.** `apply_governor()` walks every
   CPU's cpufreq sysfs files. It now re-runs only when the governor hint changes
   or every 25 ticks (~5 s) to detect external edits. Desktop behaviour is
   unchanged; QEMU has no cpufreq driver.
3. **Telemetry snapshot at 1 Hz in headless bulk mode.** Snapshot construction
   walks workloads/PIDs and serialises JSON; policy/enforcement still runs at
   the full tick rate. `titan-hwm status` is at most 1 s stale.
4. **400 ms headless tick.** The headless bulk-only sleep interval is 400 ms
   (2.5 Hz) instead of 200 ms. Desktop/Hyprland mode remains 200 ms, and all
   safety guards (bulk freeze guard, memory.high scoping, cap lift conditions)
   are unchanged.

A 1 Hz whole-tick experiment was tested and **rejected**: it cut CPU to ~6% but
slowed pressure response enough to lose hog containment (one 337 s round).
400 ms retains containment.

## Final verification — exact QEMU A/B rerun

Same VM/workload as the original regression: 2 vCPU, 4 GB RAM, 2 GB swap,
live ISO `out/archtitan-2026.11.18-x86_64.iso`,
`systemd.unit=multi-user.target`. Current daemon staged from the bench disk.

Runs: `A-20261123-121229` vs `B-20261123-122030`.

| Metric | THM v3.4-R4 | THM off | Original failing THM |
|---|---:|---:|---:|
| Complete compile rounds | 8 | 8 | 1 |
| Median complete round | **21866 ms** | 34499 ms | 468259 ms |
| THM daemon CPU | **11.92% of one vCPU** | — | 33.68% |
| Swap-out pages | 0 | 0 | 401085 |
| Kernel OOM kills | 0 | 0 | 0 |
| Min MemAvailable | 37 MB | 37 MB | — |
| Full-stall seconds | **4.4 s** | 11.2 s | 18.0 s |
| Collector tick max | 723 ms | — | — |
| Slice weights | `P:5000 / A:1000 / L:1000 / B:1000` | — | `B:10` |
| Last action | `THROTTLE (tstress)` | — | `THROTTLE (g++)` |

No compiler process was frozen. The only frozen workloads were the two idle
apps and the memory hog. The CPU cap reported `100.0% (auto-lifted: user idle
>60s)`.

### Honest caveats

- The **0.63x** median ratio in this run is not a general claim that THM is
  faster than THM-off. Arm order and host thermal/load state dominate absolute
  times; the immediately preceding R3 run was 1.17x. The robust result is that
  the original 9.8x regression stayed fixed and the absolute median remains
  **below 50 s**.
- Daemon CPU is also noisy across runs: R3 final A was 9.64%, the first R4
  200 ms A was 16.17%, and the 400 ms A was 11.92%. The deterministic wins are
  the removed `hyprctl` forks, per-tick cpufreq sysfs walk, and per-tick JSON
  serialization.
- The 400 ms tick trades some memory headroom: R3's 200 ms run had min
  MemAvailable 525 MB and 0.4 s stalls, versus 37 MB and 4.4 s here. It still
  had **61% fewer full stalls than THM-off** and no OOM. Restoring the 200 ms
  headless tick is a one-line change if maximum memory headroom is preferred.
